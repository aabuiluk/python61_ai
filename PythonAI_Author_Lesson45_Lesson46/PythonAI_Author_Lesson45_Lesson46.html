Пари 45–46 · Від LCEL до Tools і перевіреного workflow

30 хв переходу з 43–44 + 100 хв пари 45 + 100 хв пари 46 = 230 навчальних хвилин. Це план повного практикуму, а не виміряна тривалість групового заняття. Перерви та встановлення поза цим часом. Якщо маєте дві пари по 80 хв, проведіть 30 хв переходу, по 65 хв основних тем; самостійні розширення, повторні live-запуски й захист звіту — у резерві.

У 43 ви обирали framework і розділяли model/chain/retrieval/agent. У 44 склали PromptTemplate → модель → parser і відокремили історії сесій. Тепер модельний вузол одразу викликає OpenAI API. Блок 2. 44 → API · Історія двох live-сесій

15–30 хв.

Факт 2. Модель бачить тільки ту історію, яку застосунок передав у поточному запиті. Зберігаємо реальний RunnableWithMessageHistory із 44, а його модельний вузол викликає OpenAI API. Сесія A отримує кодове слово, наступна репліка просить його повторити. Новий session_id B не має цих повідомлень. Перевіряємо і поведінку моделі, і склад сховища; лише правдоподібна відповідь не доводить ізоляцію. InMemoryChatMessageHistory існує в RAM поточного процесу. Store=False в API не підміняє локальне керування історією: потрібні messages, session_id та бюджет контексту. За нових запусків скрипта починаємо з порожнього store. Це місток до коду 44 на зафіксованій версії: RunnableWithMessageHistory та InMemoryChatMessageHistory уже позначені deprecated у цій лінійці LangChain. Попередження не є помилкою запуску. Для нових виробничих агентів перегляньте short-term memory та LangGraph persistence; у 46 ми окремо зберігаємо стан workflow, а не покладаємось на RAM.

Приклад · реальний OpenAI API

api = ClassroomAPI()
store = {}
def history_for(sid):
    return store.setdefault(sid,InMemoryChatMessageHistory())
prompt = ChatPromptTemplate.from_messages([("system","Працюйте тільки з історією цієї розмови."),MessagesPlaceholder("history"),("human","{question}")])
model = RunnableLambda(lambda value: AIMessage(content=api.text(value,stage="memory")))
chat = RunnableWithMessageHistory(prompt | model,history_for,input_messages_key="question",history_messages_key="history")
chat.invoke({"question":"Кодове слово нашої вправи — Клен."},config={"configurable":{"session_id":"A"}})
answer = chat.invoke({"question":"Яке кодове слово я назвав?"},config={"configurable":{"session_id":"A"}})
show(api,{"answer":answer.content,"messages_A":len(store["A"].messages)})

Блок 3. 45.1 · LangChain @tool і схема OpenAI

30–55 хв.

Факт 3. Tool — це Python-функція, опис її призначення та схема аргументів. runtime.py оголошує lookup_ticket і get_sla через справжній декоратор @tool із langchain-core. Docstring пояснює, коли дія доречна, а type hints задають типи. convert_to_openai_function переносить цей контракт у function tool для Responses API. Назва й схема не надають моделі прямого доступу до Python: виконання відбудеться тільки через наш dispatcher. Strict schema допомагає формі аргументів, але не гарантує, що запит до обраного інструмента доречний або що заявка існує. У прикладі надсилаємо моделі самі схеми та просимо пояснити вибір. У наступних блоках виконаємо справжні function calls. Два read-only tools не змінюють заявки.

Блок 4. 45.2 · JSON-аргументи: parse → validate → dispatch

55–80 хв.

Факт 4. Аргументи моделі проходять перевірку до Python-виклику. Зовнішній рядок спочатку читаємо json.loads, потім перевіряємо object, точний набір ключів, типи та дозволені значення. Не використовуємо eval або getattr для довільних назв. Dispatcher має allowlist із двох tools і повертає ok/data або ok/error. Невідомий tool, зайвий ключ, число замість рядка й відсутня заявка — різні негативні кейси. Приклад робить реальний API-запит на JSON-аргументи, після чого Python виконує dispatch. Це ще не повний function-calling протокол: у ньому також є call_id та function_call_output, які розберемо далі. Зберігайте цю різницю в назві свого результату.

Тут усі приклади працюють тільки з навчальними файлами. Схвалення затверджує чернетку, але не запускає платіж чи надсилання повідомлення.
