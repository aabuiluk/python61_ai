Пари 49–50 · Від результату курсу до власного AI-сайту

Базовий маршрут безкоштовний: Python, Git, публічний GitHub, PythonAnywhere Beginner, локальний BM25-пошук. Ключ OpenAI для цього результату не потрібен.

2. Вступ · 10 хвилин

AI-проєкт починається з корисного рішення: який запит користувача ми обробляємо, які дані можемо використовувати, яку помилку вважаємо критичною. Модель — один із компонентів. Поруч із нею потрібні підготовка даних, перевірка результату, зрозумілий інтерфейс і спосіб виправити помилку після запуску.

Сьогодні з'єднаємо ці частини. Візьмемо готовий застосунок, розберемо його межі, розмістимо власну копію і внесемо контрольовану зміну. Уміння відтворити результат із чистої папки важливе для будь-якого наступного проєкту.

Тримайте три питання: що система знає, як це перевірити, як доставити виправлення користувачу? Наприкінці заняття покажіть відповідь на кожне через конкретний файл, тест і адресу сайту.

3. Повторення А1 · постановка задачі, Python і дані · 5 хвилин

Модулі 1–2: формулювання задачі, NumPy, pandas, статистика, візуалізація. Сформулюйте вхід, вихід і ціну помилки до вибору моделі. Прогноз числа — регресія; класу — класифікація; групування без міток — кластеризація; пошук відповіді в документах — retrieval із можливою генерацією.

Python-код має виконуватися повторно: зрозумілі функції, явні параметри, перевірка типів і діапазонів на вході, обробка очікуваних винятків. Notebook зручний для дослідження; запуск «Restart & Run All» показує, чи не залежить результат від випадково виконаних комірок. Повторювану логіку переносіть у модулі.

Для таблиці перевірте одиницю спостереження, одиниці вимірювання, пропуски, дублікати, дисбаланс і походження даних. Середнє та медіана реагують на викиди по-різному; кореляція не доводить причину. Гістограма показує розподіл, scatter — зв'язок двох ознак, групові зрізи — різницю між сегментами. Не підставляйте нулі в усі пропуски автоматично: нуль може мати предметне значення.

Мікроперевірка, 30 секунд: у таблиці заявок є closed_at. Чи можна використати його для прогнозу терміну закриття під час створення заявки? Запишіть відповідь у tasks/task_01.md.

Готово, якщо: названо момент прогнозу та ознаку, якої в цей момент ще немає.

4. Повторення А2 · supervised ML та метрики · 6 хвилин

Модуль 3: регресія, градієнтний спуск, регуляризація, дерева, ансамблі, логістична регресія. Починайте з baseline: середнє для регресії, проста стратегія для класифікації. Складніша модель повинна покращувати потрібну метрику на даних, які не використовувались для налаштування.

Розділіть train/validation/test до навчання перетворень. fit imputer, scaler, encoder або відбору ознак виконується на train; validation/test проходять transform. Pipeline і ColumnTransformer допомагають дотримуватися цього при крос-валідації. Для часових даних дотримуйтеся хронології; для повторних записів однієї людини або об'єкта розділяйте групи. Випадковий split не гарантує відсутності витоку. Практика scikit-learn.

MAE має одиниці цілі; RMSE сильніше реагує на великі промахи. R² не є відсотком правильних прогнозів. Для рідкісного позитивного класу аналізуйте precision, recall, confusion matrix та поріг рішення. Accuracy 99% може отримати модель, яка завжди відповідає «негативний», якщо позитивних лише 1%.

Навчання зменшує loss на train; regularization обмежує складність, а перевірка на відкладених даних показує узагальнення. Порівнюйте моделі на одному split і з однаковим бюджетом експериментів. Зберігайте конфігурацію та версію даних, а не лише найкраще число.

Зараз виконайте завдання 1, продовження: у tasks/task_01.md оберіть метрику для пропуску небезпечної заявки та поясніть ціну false negative. На відповідь — 1 хвилина всередині блоку.

Готово, якщо: є baseline, спосіб split, заборона fit на test та обґрунтований вибір recall/precision з ціною помилки.

5. Повторення А3 · нейромережі та комп'ютерний зір · 5 хвилин

Модулі 4–5: тензори, nn.Module, autograd, оптимізація, CNN, batches, Dropout і BatchNorm. Стежте за формою тензорів та відповідністю виходу loss-функції. У звичайній багатокласовій задачі CrossEntropyLoss отримує logits і індекси класів; додатковий softmax перед нею не потрібен.

Навчальний цикл: model.train() → forward → loss → optimizer.zero_grad() → loss.backward() → optimizer.step(). Перевірка: model.eval() і torch.inference_mode(); оцінювання не змінює ваги, а Dropout/BatchNorm мають правильну поведінку. Приклад PyTorch.

Для зображень і тексту практичний початок — придатна попередньо навчена модель та перевірка на власних даних. Спочатку оцініть її як є, потім потребу в донавчанні. Аугментації застосовуйте до train; пацієнт, пристрій чи серія пов'язаних зображень не мають випадково розходитися між train і test. Медичний навчальний приклад не є валідованим діагностичним сервісом.

Мікроперевірка: що окремо роблять eval() та inference_mode()? Перша змінює режим модулів; друга вимикає облік градієнтів для inference. Одне не замінює другого.

6. Повторення А4 · NLP, embeddings, кластери й рекомендації · 4 хвилини

Модулі 6–7: очищення тексту, токенізація, embeddings, Transformer, transfer learning, PCA/SVD, K-means/DBSCAN, рекомендації. Token — одиниця, яку обробляє модель; це не завжди слово. Embedding — числове представлення, близькість якого залежить від моделі та задачі. Cosine similarity не означає ймовірність істинності.

Для пошуку порівнюйте lexical baseline (BM25/TF-IDF), embeddings і, за потреби, hybrid retrieval або reranking на власному наборі запитів. Код товару чи номер заявки може краще знаходитися за точним збігом. Після зміни embedding-моделі перебудовуйте індекс сумісними векторами; однакова розмірність не гарантує однакового простору.

PCA/SVD стискають представлення; пояснена дисперсія не гарантує якість майбутнього прогнозу. K-means потребує кількості кластерів і чутливий до масштабу. DBSCAN може позначати шум, але результат залежить від щільності та параметрів. Кластер — знайдена структура, яку ще треба інтерпретувати.

Рекомендації перевіряйте за релевантністю top-k, покриттям і доступністю товарів; пам'ятайте про cold start та витік майбутніх взаємодій. Два різні ID у рекомендації важливіші за два красиві описи одного об'єкта.

7. Повторення Б1 · промпти, контекст і RAG · 6 хвилин

Модуль 8, пари 37–42: генерація, prompt patterns, контекст, Gemini/Google AI Studio, Vertex AI, RAG. Промпт складайте з інструкції, відокремлених даних, задачі й контракту відповіді. Few-shot приклади показують формат і межі. Просіть коротке обґрунтування через перевірювані факти й джерела; довгий текст міркувань не доводить правильність.

Контекстне вікно має бюджет. Вибирайте релевантні фрагменти, зберігайте source ID, відділяйте текст документів від дозволених дій. Інструкція «ігноруй правила» всередині документа є даними, а не дозволом змінити поведінку. Перевіряйте формат окремо від змісту: валідний JSON може містити хибні факти.

RAG: джерела → фрагменти → пошук → відібраний контекст → відповідь із посиланнями → перевірка. Якщо потрібного факту немає серед відібраних уривків, модель має повідомити про брак даних. Поліпшення retrieval і поліпшення generation вимірюйте окремо. Розмір chunk, overlap і top-k — параметри експерименту, а не універсальні константи.

Google AI Studio — робочий інтерфейс для прототипування з Gemini; Vertex AI — керована платформа GCP із проєктами, IAM і хмарними ресурсами. У цьому практикумі вони не потрібні: немає кроку активації GCP-білінгу. Доступні моделі, квоти та ціни перевіряйте в актуальній документації сервісу, а не за скріншотом заняття.

Зараз виконайте завдання 2: у tasks/task_02.md запишіть три перевірки RAG: точний факт із джерела, питання поза корпусом, шкідлива інструкція в документі. 1 хвилина всередині блоку.

Готово, якщо: кожне питання має очікувану поведінку, а відповідь «не знайдено» дозволена.

8. Повторення Б2 · API, tools і контроль workflow · 5 хвилин

Модуль 9, пари 43–46: API, шаблони повідомлень, історія, tools, routing, валідація, пауза та resume. Модель пропонує виклик інструмента; застосунок перевіряє ім'я, аргументи, дозволи і виконує його. Схема JSON описує форму аргументів, але бізнес-правила все одно перевіряє код. Для зміни даних потрібні явні межі повноважень і підтвердження там, де цього вимагає процес.

Простий визначений workflow легше перевірити, якщо етапи відомі. Агент доречний, коли справді потрібен вибір подальшої дії; установіть бюджет кроків, таймаути і критерій зупинки. Retry виконуйте обмежено; для дій із побічним ефектом врахуйте повторне виконання. Стан діалогу має ізолюватися за користувачем або сесією.

Вибирайте API та модель за задачами, які перевіряєте, і за чинним контрактом. У навчальному python61ai вже є конкретна реалізація Chat Completions у rag/llm.py. Для нових інтеграцій окремо перевіряйте чинну документацію провайдера; назва найновішої моделі не є вимогою цього деплою. Не підміняйте весь стек під час першого запуску.

9. Повторення Б3 · оцінка, спостережуваність, наступні кроки · 4 хвилини

Пари 47–48: trace, latency, usage, golden cases, RAG-практикум, оцінка й людська перевірка. Зберігайте ID запиту, версію корпусу/промпта, знайдені source ID, час, статус і помилку. Ключі та персональні дані в лог не записуйте. Trace пояснює послідовність виконання; метрика підсумовує результати на наборі випадків.

Golden set містить питання, очікуване джерело/факт, припустиму відмову та правило перевірки. Перевіряйте retrieval hit@k, підтримку тверджень джерелами, коректність цитат, частку відмов, затримку та витрати. LLM-as-judge допомагає з масштабуванням перевірок, але потребує рубрики та звірки з людськими оцінками. Підхід до evaluation.

У подальшій роботі рухайтеся циклом: невеликий кейс → baseline → відкладені перевірки → одна зміна → порівняння → реліз → моніторинг. Не змінюйте одночасно модель, chunking і промпт, якщо хочете зрозуміти причину результату. Зберігайте working version і шлях повернення до неї.

Готово, якщо: у tasks/task_02.md додано, що перевіряти до релізу та яку помилку контролювати після нього.

11. Fork і локальний запуск · хвилини 03–13

На GitHub відкрийте aabuiluk/python61ai → Fork → Create a new fork. Owner — ваш акаунт; назва — python61ai; залиште main. Відкрийте власний fork, натисніть Code → HTTPS і скопіюйте адресу.

На ПК, у Terminal/PowerShell:

git clone https://github.com/GH_LOGIN/python61ai.git
cd python61ai
git remote -v
python -m venv .venv

Перед першим комітом задайте автора для цього репозиторію, якщо ще не налаштовано: git config user.name "Ваше ім'я" та git config user.email "Ваша GitHub noreply адреса". GitHub noreply email знайдете у власному Settings → Emails. Це підпис коміту, а не спосіб авторизації.

Активуйте середовище: Windows PowerShell — .\.venv\Scripts\Activate.ps1; macOS/Linux — source .venv/bin/activate. Якщо PowerShell блокує активацію, не змінюйте системну політику: виконуйте команди через .\.venv\Scripts\python.exe замість python.

python -m pip install -r requirements-dev.txt

Windows, перед тестами: у перевіреній ревізії проєкту SQLite-з'єднання в тестах не закриваються перед видаленням тимчасового каталогу. Це спричиняє WinError 32 у cleanup. Із цього роздатка скопіюйте examples/windows_sqlite_cleanup.patch до кореня власного форка. Перегляньте патч: він додає Store.close() і закриває ресурси тестів, не змінює пошук чи відповіді. У корені форка:

git apply --check windows_sqlite_cleanup.patch
git apply windows_sqlite_cleanup.patch
git diff --stat
git add rag/store.py tests/test_admin.py tests/test_rag.py
git commit -m "Close SQLite resources before test cleanup"

Сам файл патча до коміту додавати не потрібно. Якщо --check повідомляє, що патч не застосовується, не запускайте другу команду: можливо, upstream уже виправлений або змінився. Перевірте Store.close і tearDown; на актуальному виправленому коді патч пропускаємо. На macOS/Linux цей дефект зазвичай не блокує видалення відкритого файлу; коректне закриття ресурсів корисне на всіх ОС. Далі на будь-якій ОС:

python -m unittest discover -s tests -t . -v
python app.py

17. Перевірка, діагностика та повернення · хвилини 64–75

Із папки цього роздатка (це окрема папка від коду застосунку):

python examples/example_01.py https://PA_LOGIN.pythonanywhere.com
python examples/example_02.py https://PA_LOGIN.pythonanywhere.com --marker СОНЯХ-61

Перший скрипт перевіряє health без виклику генерації; другий — конкретне слово в результатах /api/search. Якщо у завданні 5 ви змінили слово, передайте його через --marker. HTTP 200 доводить доступність маршруту, але лише перевірка фрагмента доводить доставку нового знання. Обидва скрипти використовують стандартну бібліотеку.

Симптом Де перевіряти Дія
Push не дозволено git remote -v Origin повинен бути вашим fork; пройдіть GitHub-авторизацію

18. Резервний ручний шлях: без PA API

Це запасний сценарій, якщо API-токен/Actions тимчасово недоступні; він замінює відповідні кроки, а не додається до 75 хвилин. У власному новому PythonAnywhere: Consoles → Bash:

git clone https://github.com/GH_LOGIN/python61ai.git ~/rag_manual

Створіть вебапку Web → Add a new web app → Manual configuration, запишіть обрану версію Python. Для публічного бота в безкоштовному режимі venv не обов'язковий. Відкрийте посилання WSGI configuration file у Web і замініть його приклад на:

import os
import sys
os.environ["RAG_USE_LLM"] = "0"
os.environ["RAG_DATA_DIR"] = "/home/PA_LOGIN/rag_data_manual"
sys.path.insert(0, "/home/PA_LOGIN/rag_manual")
from app import application

У цьому платформному WSGI імпорт from app import application правильний: абсолютний шлях до кореня застосунку вже додано в sys.path, а PythonAnywhere очікує ім'я application. Це не імпорт спільного навчального runtime. Замініть обидва PA_LOGIN своїм логіном, Save → Web → Reload. Перевірте health. Не запускайте python app.py у консолі як спосіб постійного хостингу.

Для наступного оновлення спочатку push з ПК у свій fork, потім у PA Bash: cd ~/rag_manual, git pull --ff-only origin main, далі Web → Reload. Поки обраний цей ручний шлях, залиште автоматичний workflow вимкненим: він перепише WSGI і переключить сайт на rag_site. Адмінка в ручному мінімальному варіанті може відповідати 503; для неї створіть venv з тією самою версією Python, встановіть requirements, укажіть venv у Web і додайте приватний .env у корінь застосунку з ADMIN_PASSWORD. Публічний пошук працює і без адмінки.
