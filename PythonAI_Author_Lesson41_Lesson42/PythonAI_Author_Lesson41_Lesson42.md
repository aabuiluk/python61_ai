# Основний маршрут 41–42: локально + OpenAI API

## RAG і локальний векторний пошук з OpenAI API

- Концепція RAG: пошук у власних документах → контекст → відповідь OpenAI API.
- Локальна інтеграція текстів, PDF і CSV: читання, очищення, чанки та метадані джерел.
- Реальні embeddings через OpenAI API; індексація та cosine/top-k пошук локально на комп’ютері.
- Створення локальної бази знань: документи, embeddings, індекс і збереження на диск.
- Формування RAG-запиту, посилання на джерела, перевірка JSON і відмова від вигаданих фактів.
- Оцінювання retrieval, recall@k, підтримки фактів і витрат API; захист від інструкцій у документах.
- Практика: український магазин — TXT/PDF/CSV → локальний індекс → реальна відповідь OpenAI.
- Vertex AI / Vector Search / Agent Builder — коротке порівняння з хмарною архітектурою, без обов’язкового GCP-проєкту.

## LLM-агенти та локальний GenAI-застосунок з OpenAI API

- Архітектура AI-агента: локальний інтерфейс → OpenAI API → дозволені інструменти → локальні дані.
- Tools і Function Calling: JSON Schema, allowlist, валідація аргументів і повернення результату моделі.
- Локальна оркестрація: історія діалогу, стан, ліміт кроків, таймаути та обробка помилок API.
- Шаблони ReAct Agent, Planner–Executor і Knowledge Retriever Agent на одному практичному сценарії.
- RAG як інструмент агента: локальна база знань і справжні запити до OpenAI API.
- LangChain / LangGraph / ADK: роль фреймворку; Agent Engine — необов’язкове порівняння з керованим runtime.
- Спостережуваність і безпека: tool trace, latency, token usage, витрати, .env і захист даних.
- Практика: локальний Streamlit / Gradio або FastAPI → OpenAI API → локальний vector search / RAG → агентний цикл.
- Запуск і демонстрація застосунку на localhost; Docker — додатково. GCP-деплой не є умовою виконання.

## Встановлення з кореня python61_ai

## TXT, PDF і CSV → локальні документи

### Теорія
TXT читаємо як текст, PDF — по сторінках, CSV — по рядках із назвами колонок. Кожен запис зберігає id, text, source, а також page або row. Після цього чанки зберігають document_id і початкову позицію. Для сканованого PDF потрібне OCR; pypdf читає наявний текстовий шар. Усі дані цього прикладу — вигадані правила та товари українського магазину.

### Приклад
local_products.csv: lamp → «Настільна лампа коштує 850 грн», source=local_products.csv, row=2. local_delivery.pdf → текст першої сторінки з source та page=1.

Файл: local_runtime/ingest.py

### Практика
Після прикладу виконайте L01: прочитайте 3 файли, отримайте 4 документи та перевірте source/page/row. Додайте свій товар. Змініть розмір чанків і overlap, перевірте ID. API на цьому кроці ще не потрібний.

```bash
python local_runtime/ingest.py
```

## Справжні embeddings OpenAI → локальний vector search

### Теорія
Embeddings отримуємо через справжній OpenAI API з власним ключем. text-embedding-3-small перетворює тексти на вектори. Вектори, документи, назва моделі та розмірність зберігаються у results/local_index.json на вашому комп’ютері. Пошук top-k і cosine виконуються локально в NumPy; хмарний vector database не потрібний. Для запиту використовуємо ту саму embedding-модель. Косинусна схожість не є ймовірністю правдивості; поріг відбору потрібно перевіряти на власних питаннях.

### Приклад
Документи один раз відправляються в embeddings.create; індекс записується на диск. Для питання створюється query embedding, потім локально рахується matrix @ query. Команда ask передає знайдені фрагменти у реальний Responses API.

Файл: local_runtime/vectors.py

### Практика
L02: побудуйте індекс із власним .env. Відкрийте JSON, перевірте embedding_model і dimensions. Знайдіть лампу прямим питанням і перефразуванням. L03: виконайте два ask, перевірте JSON answer/sources та вручну зіставте факти. Зафіксуйте usage embedding та генерації окремо.

```bash
python local_runtime/vectors.py build
python local_runtime/vectors.py search "Скільки коштує лампа?"
python local_runtime/vectors.py ask "Яка доставка Україною?"
```

## Локальна Knowledge Base, збереження та перевірка RAG

### Теорія
База знань складається з джерел, метаданих, чанків, embedding-моделі та індексу. Індекс можна завантажити з JSON без повторної індексації всіх документів. Після зміни корпусу або моделі потрібен узгоджений rebuild. Відокремте якість retrieval від правильності відповіді: recall@k перевіряє знайдені джерела, а перевірка тверджень — підтримку фактів. Порожній контекст не повинен спричиняти вигадування. Валідний ID ще не доводить, що відповідь випливає з тексту.

### Приклад
Після індексації перезапустіть процес, виконайте search і отримайте той самий локальний корпус. Для невідомої ціни відповідь має визнати відсутність даних, навіть якщо тематично близький фрагмент знайдено.

Файл: local_runtime/vectors.py

### Практика
L04: складіть 5 питань із очікуваними source та один відсутній факт. Порахуйте recall@2, перевірте невідомий ID, зіпсований JSON і prompt injection у копії документа. Порівняйте TF-IDF з embeddings на однакових питаннях; не підміняйте живі результати fixtures.

```bash
python local_runtime/vectors.py search "Яка доставка Україною?"
```

## Tools, Function Calling та локальна оркестрація

### Теорія
Інтерфейс → OpenAI API → function_call → локальна валідація → Python-tool → function_call_output → OpenAI API → відповідь. Модель обирає дію, ваш код виконує її. get_product повертає перевірені price_uah/stock, search_knowledge читає локальний індекс. Усі інструменти працюють у вашому процесі; embedding-запит та LLM-відповіді використовують реальний API. Ліміт у прикладі — три модельні запити, плюс окремі embeddings для retrieval.

### Приклад
run_agent отримує call_id і додає результат з тим самим call_id до історії. Невідоме ім’я або зайвий аргумент повертає контрольовану помилку. Імпорт модуля не запускає API-виклики.

Файл: local_runtime/agent.py

### Практика
L05: після готового прикладу виконайте комбіноване питання. Покажіть два tools, call_id і фінальну відповідь. Перевірте allowlist, типи, зайві параметри й вичерпання ліміту. Записуйте назви tools, час та usage без ключів.

```bash
python local_runtime/agent.py "Яка ціна лампи і доставка Україною?"
```

## ReAct, Planner–Executor, Knowledge Retriever та фреймворки

### Теорія
ReAct — повторюваний цикл дії й observation: наступний tool залежить від попереднього результату. Planner–Executor спочатку створює обмежений план, перевіряє дозволені кроки та виконує їх. Knowledge Retriever спеціалізується на поверненні документів і source. Усі три шаблони можна реалізувати локальними функціями. Не вимагайте прихованих міркувань: перевіряйте видимі tool calls і результати. LangChain, LangGraph або ADK допомагають організувати код і стан; вони не є обов’язковими для першого агента.

### Приклад
У agent.py є run_agent для циклу і execute_plan для плану. search_knowledge є окремим retriever-tool. Зберігаючи ці контракти, пізніше можна перейти на фреймворк. Agent Engine — кероване середовище виконання для порівняння, а не вимога практики.

Файл: local_runtime/agent.py

### Практика
L06: перевірте валідний план із двох кроків, невідомий tool і план із чотирьох кроків за max_steps=3. Виконайте валідний план із живим retrieval. L07: порівняйте його trace із ReAct на тому самому питанні.

```bash
Відкрийте local_runtime/agent.py → execute_plan та tasks/local_L06.py.
```

## Локальний GenAI-застосунок: Streamlit / Gradio / FastAPI

### Теорія
Основна архітектура: локальний frontend → LLM-логіка OpenAI API → локальний vector search/RAG → локальний агентний цикл. Дані, індекс, інструменти, стан і UI працюють на комп’ютері. Підготовлений Streamlit показує режими RAG та Агент. Gradio або FastAPI — альтернативний інтерфейс із тим самим backend-контрактом. Для виконання не потрібні GCP-проєкт, Google IAM чи Gemini API.

### Приклад
Спочатку побудуйте results/local_index.json, потім запустіть Streamlit. Відкрийте localhost і поставте питання про доставку, а в режимі агента — про ціну та доставку. За бажанням додайте /health і /ask у FastAPI або Docker, не змінюючи джерело ключа.

Файл: local_runtime/app.py

### Практика
L08: запустіть UI на localhost, перевірте обидва режими, відсутній факт і помилку контракту. Здайте код, 5–6 локальних тестів, два реальні RAG-запити та один реальний агентний цикл. Покажіть token usage/latency й обмеження, без секретів у журналі.

```bash
streamlit run local_runtime/app.py
```
